# 客服意图与工单微调：阶段路线图

当前状态：初始化完成，开发尚未开始。以下任务均为计划。

整体路线：企业知识库问答 → 智能客服工作台 → 客服意图与工单微调。三个项目分别交付，按验收推进。

| 周 | 要学什么 | 当周可检查的产出 |
| --- | --- | --- |
| 13 | PyTorch 张量、梯度、交叉熵；SFT、LoRA 与 RAG 的分工 | 建立客服意图与工单字段的未微调基线；明确标签定义、缺失字段表示、预期 JSON 和预算 |
| 14 | 数据标注、去重、训练/验证/测试划分 | 在前两阶段持续积累的基础上，争取整理 200～500 条人工审核样本；按问题来源分组划分数据；先冻结至少 40 条独立测试案例 |
| 15 | Tokenizer、聊天模板、训练损失与 LoRA 参数 | 先用少量样本跑通训练、保存和重新加载；再做一次完整的小规模训练，保留模型版本与环境 |
| 16 | 过拟合、验证集选参、分类与字段提取指标 | 使用验证集比较参数与错误案例；比较规则基线、同一小模型的提示基线和微调模型，保持输入与约束一致 |
| 17 | 推理集成、失败回退、最终独立测试 | 将微调模型作为项目二的可选客服分流组件；在冻结测试集上记录意图 Macro-F1、字段匹配、JSON 合法率、延迟和硬件 |
| 18 | 实验可复现性、模型与数据说明、开源发布 | 项目三 v0.1：训练/评测命令、配置、数据说明、对比报告；串起三项目演示，并明确推荐使用哪种方案 |

## 阶段验收

- 任务只做少量明确的客服意图分类，以及从会话提取产品、问题现象、相关服务标识等工单字段；字段缺失时明确标记，不补造客户信息。
- 初始意图可采用「产品使用、账号访问、套餐服务、故障反馈、其他」；按真实样例再收敛定义。信息不足的输入须标注澄清需求，模型生成的标签须人工审核。
- 同一客户案例、会话及其改写不能跨训练集与测试集；测试集不参与提示选择与参数调整。可公开样例使用虚构身份，真实客服记录先落实使用授权与隐私处理。
- 对规则方案、同一基础模型加提示、微调模型做同条件比较，报告准确数量、分类 Macro-F1、字段匹配率和 JSON 合法率。对延迟和成本分别记录硬件与计费方式。
- 微调没有优势时，保留更简单的基线作为项目二默认方案；公开负结果与原因也是完整交付。
- GitHub 保存训练与评测代码、配置和报告。权重如需分享，使用合适的模型托管方式并先核对基础模型许可。

## 首版交付要求

- README 中说明实际可用的功能、运行步骤和限制。
- 提供可公开的虚构客服样例输入与输出，说明数据来源与隐私边界。
- 保留评测用例、结果和失败案例。
- 普通自动检查使用离线样例；在线模型评测单独运行，避免自动消耗 API 配额。
- 在干净环境中复核运行步骤后再发布 v0.1。

200～500 条是初始数据准备目标，不代表足够或必然提升。测试集不参与提示选择和参数调整；微调没有优势时，记录结论并保留更简单的基线。
